# Model Storage Locations

**Summary**: Where Draw Things and ComfyUI keep their model weights after the 2026-10-01 move to an external SSD, how each tool is pointed at them, and the one case that does not work (the Draw Things GUI).

**Sources**: measured on this machine 2026-10-01; no external source.

**Last updated**: 2026-10-01

---

## Current layout

```
/Volumes/KExtreme SSD/
  DrawThingsModels/     155.8 GB, 67 files   <- draw-things-cli, via DRAWTHINGS_MODELS_DIR
  ComfyUI-Shared/        42.0 GB,  8 files   <- ComfyUI, via a symlink from ~
```

| Consumer | How it finds models | Works? |
|---|---|---|
| `draw-things-cli` (all of `scripts/`) | `DRAWTHINGS_MODELS_DIR` in `~/.zshrc` | yes |
| ComfyUI | `~/ComfyUI-Shared` → symlink to the SSD | yes |
| Draw Things **GUI** | its sandbox container path, now holding only manifests | **no models** |

The drive is a SanDisk Extreme 2 TB, APFS, `/dev/disk5s1`.

## Draw Things CLI

`draw-things-cli` resolves models in this order:

```
--models-dir  ->  DRAWTHINGS_MODELS_DIR  ->  ~/Library/Containers/com.liuliu.draw-things/Data/Documents/Models
```

`~/.zshrc` sets the middle one:

```bash
export DRAWTHINGS_MODELS_DIR="/Volumes/KExtreme SSD/DrawThingsModels"
```

`scripts/preflight.sh` already honoured this variable before the move, so it checks the right
place with no change. It is the fastest way to confirm the drive is mounted and the models are
visible — a missing drive shows up as a failed model check, not as a confusing error mid-render.

**`.zshrc` is read by interactive shells only.** `zsh -ic` resolves the variable; `zsh -lc`
returns empty. Running `film_run.py` from a terminal inherits it. A `cron` or `launchd` job would
not, and would silently fall back to the empty container folder.

## ComfyUI

Comfy Desktop writes its own config and marks it *"Generated by Comfy Desktop — do not edit
manually"*:

```
~/Library/Application Support/Comfy Desktop/instance-model-paths/inst-*.yaml
  base_path: '/Users/kevinyang/ComfyUI-Shared/models'
```

Rather than edit a file the app regenerates, `~/ComfyUI-Shared` is a symlink to the SSD. The
configured path keeps working untouched, and survives app updates. `input/` and `output/` moved
with it, so generated video also lands on the SSD.

ComfyUI fails *quietly* when the drive is absent: it starts normally and shows empty model
dropdowns. If models vanish from the UI, check the mount before anything else.

## The Draw Things GUI does not work this way

The app is sandboxed and reads its container path directly; it does not know about
`DRAWTHINGS_MODELS_DIR`. Symlinking the container folder to the SSD was tried on 2026-10-01 and
**the GUI did not detect the LoRAs**, even though:

- 57 `.ckpt` files resolved through the link from a shell
- `stat` through the link returned correct sizes
- all 34 entries in `custom_lora.json` pointed at files that exist
- no sandbox denial and no TCC denial appeared in `log show`
- the app was quit and relaunched so it could not be a stale scan

The symlink was removed. The container folder now holds only the four manifests
(`custom.json`, `custom_configs.json`, `custom_lora.json`, `custom_prompt_style.json`), which are
kept so the app does not regenerate defaults and lose the LoRA registry.

One likely contributor, unproven: the volume reports `Owners: Disabled`, so macOS ignores POSIX
ownership on it. A sandboxed app's file-access checks need not behave like the shell's.

To use the GUI again, copy the needed weights back into the container folder — roughly 8.5 GB for
klein, 24 GB for LTX-2.3, 13 GB for all trained LoRAs. The CLI keeps reading the SSD either way.

**Watch for drift:** `custom_lora.json` now exists in both places. If the GUI registers a new LoRA
it edits the internal copy while the CLI reads the external one. Harmless while the GUI has no
models; worth syncing if that changes.

## Moving models: what the copy has to include

- **`-tensordata` sidecars travel with their `.ckpt`.** Draw Things splits large weights out:
  `umt5_xxl_encoder_q8p.ckpt` is 880 KB and its data is a separate 6.4 GB file. The `.ckpt` alone
  is useless.
- **The four `custom*.json` manifests are required.** Without them `draw-things-cli` reports
  `DOWNLOADED: no` for every model and `--model` fails to resolve, even with the weights present.
  This is the single most confusing failure in the move — the files are there and nothing works.
- Verify by comparing raw byte totals, not `du`. APFS clone and sparse accounting made `du` report
  134 GB for a tree whose files sum to 155.8 GB.

## Performance

Measured 2026-10-01, FLUX.2 klein 9B, 1024x576, 4 steps:

| | total (incl. load) | median step |
|---|---|---|
| internal, warm | 17.27 s | 3.16 s |
| external, cold | 39.73 s | 3.20 s |
| external, warm | 17.42 s | 3.17 s |

**Sampling speed is unchanged.** Step time is GPU work in unified memory; the disk is not in the
loop once weights are resident. The only cost is the cold read, ~22 s for klein + its Qwen 3 8B
text encoder (~17 GB), which works out to ~770 MB/s.

With 48 GB of RAM, klein and LTX cannot both stay resident, so each model switch pays a cold load.
`film_run.py` does all stills then all clips — about two cold loads per film, roughly **+1 minute**
against ~88 minutes of LTX rendering. Under 1%.

**Check the link speed before trusting the drive.** The same SSD first benchmarked at 27.8 MB/s
because it had negotiated USB 2.0:

```bash
system_profiler SPUSBDataType | grep -A6 "Extreme 55AE"
```

`Speed: Up to 480 Mb/s` is the bad case (a charge-only USB-C cable will do this). `Up to 10 Gb/s`
is correct and gives ~805 MB/s. At 480 Mb/s the 24 GB LTX model takes ~15 minutes to load.
