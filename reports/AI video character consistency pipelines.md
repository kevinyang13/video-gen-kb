# ControlNet unlocks your Mac pipeline's missing determinism

**The single most consequential finding in this research is a correction, not a discovery: `draw-things-cli` reaches ControlNet headlessly through a `controls[]` array inside `--config-json`, not through a command-line flag — so the conclusion that the CLI's 23 flags ruled out structural conditioning on this machine was wrong.** The same config surface exposes `loras[]`, inpainting, refiner and hires-fix keys, because `--config-json` accepts every `JSGenerationConfiguration` key the GUI exposes ([draw-things-community](https://github.com/drawthingsai/draw-things-community); recorded in `wiki/headless-cli-pipeline.md` §1). That one fact moves this project from the regime it is in now — generate three candidates, score them, hope — into the regime professional pipelines actually operate in, where **structure is supplied as an image and identity is supplied by a trained adapter, and the sampler is asked to render a planned shot rather than to roll one.** The rest of the picture is less flattering but equally actionable: the identity half of the conditioning stack (IP-Adapter, InstantID, PuLID) has no confirmed working MPS report and is structurally incapable of representing a vehicle anyway; the one rigorous object-fidelity benchmark in existence puts FLUX.2 Klein 9B — this project's still model — last of four at **16.8% clean passes with 28% outright invalid outputs** ([Photoroom](https://photoroom.com/blog/top-editing-image-models-maintain-product-details-only-28-of-the-time)); and **no published test anywhere holds a made-up mechanical object across multiple shots**, which means the benchmark this film needs does not exist and could be generated here more cheaply than it could be found. The practical conclusion is a staged rebuild: keep the model-sheet masters, combo masters and edit-off-combo rule that already match professional practice, add depth/canny conditioning from a coarse 3D proxy of the skiff, and replace candidate ranking with a conditioning schedule.

## Draw Things reaches ControlNet through config JSON, not through a flag

The CLI's flag list is a red herring. Configuration precedence runs model-recommended settings → `--config-json`/`--config-file` → explicit flags, and the JSON layer accepts the full `JSGenerationConfiguration` schema read from `Libraries/Scripting/Sources/ScriptModels.swift` and `Libraries/DataModels/Sources/config.fbs` — which includes **`controls[]` (ControlNet), `loras[]`, `refinerModel`/`refinerStart`, `hiresFix*`, `stage2Steps`/`stage2Guidance`/`stage2Shift`, `stochasticSamplingGamma`, `causalInference`, `teaCache*`, `upscaler`, `numFrames` and `fps`** ([draw-things-community](https://github.com/drawthingsai/draw-things-community), as recorded in `wiki/headless-cli-pipeline.md` §1). The GUI's advertised ControlNet support is therefore not GUI-only: the App Store listing's "full ControlNet support" and on-device LoRA training ([Draw Things on the App Store](https://apps.apple.com/us/app/draw-things-offline-ai-art/id6444050820)) both have headless equivalents. A second headless route exists as well — `gRPCServerCLI-macOS <models dir> --no-response-compression --model-browser` on port 7859, driveable from the official [draw-things-comfyui](https://github.com/drawthingsai/draw-things-comfyui) extension or any gRPC client — which matters only if rendering ever moves to a second Mac, since there is no published API reference and the schema has to be read from `imageService.proto`.

What this unlocks is specific and large. **Per-shot geometry becomes an input rather than an outcome.** A depth map or canny edge map of the skiff, rendered from a camera you chose, can be handed to the same klein render that currently gets only a prompt and a reference image — which means hull proportions, nacelle placement, ground contact, subject scale and framing stop being re-rolled per seed. It also means the two failures documented in `wiki/shot-locks.md` have a structural fix rather than a prompting fix: the "flat delta-wing" that replaced the skiff whenever the model had to invent a yard around it, and the "angular cardboard shape" in s7, are both the signature of layout being decided by noise in the first few sampling steps with nothing holding it.

What it does **not** unlock is equally important, and four limits are firm. First, **ControlNet is the structural half only — it carries no identity at all** and is "almost always paired with a LoRA or IP-Adapter" ([DEV: LoRA + ControlNet + IPAdapter](https://dev.to/rashid_inmarketing_19a21d/maintaining-character-consistency-in-comfyui-lora-controlnet-ipadapter-5883)). Second, **per-reference Moodboard weights are not reachable from the CLI**: `setMoodboardImageWeight(weight, index)` exists only in the in-app JS scripting layer (`Libraries/Scripting/Sources/SharedScript.swift`), and a script must be launched from inside the app, so that route is not headless. Third, the **repeatable multi-`--image` form exists only in `main`, not in the shipped binary** (`1.20260430.0`); building `main` from source was attempted on this machine and failed compiling `ccv_nnc_mfa` Metal kernels at step 524/1254 after a ~25-minute dependency fetch. The shipped `--image` is a single img2img input, which is why the diptych trick exists at all — and that version gate should be re-checked against the Homebrew formula before designing around the workaround, since a newer release would remove the need for it. Fourth, the A1111-compatible HTTP API on port 7860 **has no vocabulary for Moodboard or video** and is not a route for a conditioning-heavy pipeline.

One measured behaviour is worth restating because it is the existing identity mechanism and it is better than it looks: with klein 9B, `--strength` 0.7/0.8/0.9 is plain weak img2img — even 0.9 returns nearly the input — while **`--strength 1.0` switches klein into edit mode**, where the image becomes a reference and the prompt becomes an instruction. That is what makes both the diptych and the edit-off-combo rule work, and it is already the right primitive.

## Eight Apple Silicon dead ends, with the evidence class for each

These can stop consuming attention. The distinction between "proven broken" and "no confirmed report" is preserved deliberately, because two of the most consequential entries fall in the weaker category.

| Ruled out | Evidence class | Basis |
|---|---|---|
| **FP8 checkpoints** | Proven broken, still open | Metal has no `Float8_e4m3fn` dtype; loading fails with an explicit dtype error ([ComfyUI #6859](https://github.com/Comfy-Org/ComfyUI/issues/6859)), and a Comfy-Org discussion from **April 2026** still reports FP8 crashing on MPS with only a local file patch as a workaround — a patch one user reports being overwritten by the next update ([discussion #13273](https://github.com/Comfy-Org/ComfyUI/discussions/13273)). The fix is a different file, not a different flag. |
| **Triton** | Proven unavailable | No CUDA, no Triton ([comfyui-mcp skill](https://github.com/artokun/comfyui-mcp/blob/main/plugin/skills/triton-sageattention/SKILL.md)). |
| **SageAttention** | Proven unavailable | Imports `triton`; failure signature is `No module named 'triton'`. Mac remedy is attention mode **sdpa**, not installing the package ([ComfyUI #12698](https://github.com/Comfy-Org/ComfyUI/issues/12698)). |
| **xformers / flash-attention** | Proven unavailable | No Metal backend; PyTorch sdpa is the substitute (same skill source). |
| **torch.compile / inductor** | Proven unavailable | Compiles through Triton; the guidance is to avoid those nodes entirely (same source). |
| **Nunchaku (SVDQuant 4-bit)** | **Absence of evidence** | No Mac support statement found anywhere; install docs mention macOS only for Homebrew-installing `uv`, and it is built on NVIDIA kernels ([installation docs](https://nunchaku.tech/docs/ComfyUI-nunchaku/get_started/installation.html)). Treat as unsupported, but note this is not a published refusal. |
| **ai-toolkit FLUX LoRA training on MPS** | Documented failure, closed | A FLUX.2-dev character LoRA on MPS "could not get stable loss convergence despite extensive experimentation"; the issue was **closed as not planned** with no working config posted ([ai-toolkit #871](https://github.com/ostris/ai-toolkit/issues/871)). Supporting mechanism: bitsandbytes' Metal backend has QLoRA and LLM.int8() but **8-bit optimizers still "in progress"** ([bitsandbytes on PyPI](https://pypi.org/project/bitsandbytes/)) — 8-bit Adam is exactly the saving FLUX trainers rely on. Separately, diffusers' own FLUX docs note rank-16 training with all components can exceed **40 GB** ([diffusers FLUX dreambooth README](https://huggingface.co/byyange/QwenTest/blob/main/pythonProject/diffusers-main/examples/dreambooth/README_flux.md)), above this machine's usable budget once macOS takes ~8 GB. |
| **IP-Adapter / InstantID / PuLID** | **No confirmed working MPS report** — plus a structural blocker | The canonical IP-Adapter failure is a hard-coded CUDA device move, `Torch not compiled with CUDA enabled` ([IP-Adapter #95](https://github.com/tencent-ailab/IP-Adapter/issues/95)) — but that issue is roughly 1,090 days old and may predate current `ComfyUI_IPAdapter_plus`. A recent M4 Mac mini report is a *different* failure: the loader lists no models despite correct placement ([ComfyUI #7458](https://github.com/comfyanonymous/ComfyUI/issues/7458)). PuLID's documented limitation is precision-shaped (FLUX FP8 needs bf16) plus InsightFace/AntelopeV2 dependencies ([ComfyUI-PuLID-Flux](https://github.com/balazik/ComfyUI-PuLID-Flux)); InstantID needs its own model folder, antelopev2 **and** a separate ControlNet ([InstantIDModelLoader](https://comfy.icu/node/InstantIDModelLoader)). Corroborating absence: **IP-Adapter is not in mflux's feature list at all**, despite mflux listing ControlNet, Redux, depth, inpainting, multi-image editing and LoRA training ([mflux](https://github.com/mflux-community/mflux)). |

The honest framing on the last row is that **no 2026-dated issue tests `ComfyUI_IPAdapter_plus` on MPS in either direction.** The absence of recent confirmations is the finding, and it is weaker than a dated reproduction would be. But for this film it does not matter, because of a second argument that is not probabilistic at all: **every tool in the FaceID class derives its conditioning from an InsightFace/ArcFace face-recognition embedding** — IP-Adapter FaceID uses "face ID embedding from a face recognition model instead of CLIP image embedding" from InsightFace's `buffalo_l` ([IP-Adapter-FaceID model card](https://huggingface.co/h94/IP-Adapter-FaceID)) — and a face-recognition network has no representation for a hover-skiff or a repair droid. **Face-only versus general-subject is determined by the embedding source, not by branding.** Even a working MPS port of PuLID would be useless for two of this film's three recurring assets. The FaceID branch also carries a non-commercial research licence, which the ControlNet/Fill/LoRA path does not. The practical consequence is that the Mac-friendly determinism stack is exactly the InsightFace-free one: **ControlNet, inpainting, klein edit-mode references, Qwen/Kontext-style multi-reference editing, and trained LoRAs.**

## Determinism comes from conditioning schedules, not from conditioning weights

The strongest single pattern in the practitioner literature is not a number — it is *when* each signal is active. In both A1111 and ComfyUI, `start_percent`/`end_percent` are **hard on/off switches, not fades**: setting start to 0.5 means the first half of denoising happens with the ControlNet entirely off ([Easton Dev, 2026-07-19](https://eastondev.com/blog/en/posts/ai/20260719-comfyui-controlnet-guide/)). Because shape is decided in the earliest steps, **`start_percent = 0` is the setting that makes composition deterministic** — a ControlNet that switches on late is watching layout get re-rolled per seed, which is precisely the current failure mode. The complementary half of the pattern is release: identity conditioning is run at modest weight and **ended around 0.8** so the LoRA's learned features reassert in the final steps, and pose is released near the end so style can resolve ([DEV: LoRA + ControlNet + IPAdapter](https://dev.to/rashid_inmarketing_19a21d/maintaining-character-consistency-in-comfyui-lora-controlnet-ipadapter-5883)). The consensus production order follows: base model → LoRA → identity conditioning → structural ControlNet → sample at a fixed seed → masked fix-up pass → upscale. **Structure front-loaded at 0, identity released at roughly 0.65–0.8, the last ~20% of steps left free for texture.** Practitioners who set everything to 1.0 for the full window get the "overcooked" and "rigid, artificial" outputs that multiple sources diagnose.

Only one source in this entire research publishes a per-mode strength table from a primary model card, and it is the number to start from:

| Shakker-Labs FLUX.1-dev ControlNet Union Pro 2.0 | `controlnet_conditioning_scale` | `control_guidance_end` |
|---|---|---|
| Canny | 0.7 | 0.8 |
| Soft edge | 0.7 | 0.8 |
| Depth | **0.8** | **0.8** |
| Pose | 0.9 | **0.65** |
| Gray | 0.9 | 0.8 |

Source: [Shakker-Labs/FLUX.1-dev-ControlNet-Union-Pro-2.0](https://huggingface.co/Shakker-Labs/FLUX.1-dev-ControlNet-Union-Pro-2.0). Note the pose row: highest strength, earliest release — pose maps are sparse and artifact if held to the end. The v2 release notes also **remove tile support** and add soft edge, so a v1 recipe does not transfer cleanly.

**Two node defaults are actively wrong and will waste runs.** The `FluxUnionControlNetApply` node ships **strength 1.0 on a 0–10 range** ([node listing](https://comfy.icu/node/FluxUnionControlNetApply)) — far above every published recommendation, where node documentation advises 0.15–0.65 and warns that going higher "on a union model overcooks it fast" ([ControlAltAI node docs](https://www.runcomfy.com/comfyui-nodes/ControlAltAI-Nodes/flux-union-control-net-apply)). `WanVaceToVideo` ships **strength 1.0 on a 0.0–1000.0 range** with the documentation explicitly warning it is not a LoRA strength ([ComfyUI node docs](https://docs.comfy.org/built-in-nodes/conditioning/video-models/wan-vace-to-video)) — and **no source found publishes a recommended VACE strength band at all.** In both cases the default sits at a round number that tells you nothing about the useful range. A related silent failure: if control appears to do nothing on a union model, check that the `SetUnionControlNetType` dropdown matches the map you fed, because a depth map in canny mode simply will not bite.

Three more scheduling-adjacent facts bear on the design. **Depth pins geometry harder than anything else available** and is the recommended first ControlNet to test, being "more forgiving than Canny"; stacking two ControlNets at 1.0 means one dominates, and the suggested split is depth 0.4–0.5 plus canny 0.3–0.4 for a combined ~0.7–0.9 ([Easton Dev](https://eastondev.com/blog/en/posts/ai/20260719-comfyui-controlnet-guide/)). **BFL has deprecated its own FLUX.1 Depth and Canny models in its API**, leaving the HF checkpoints "for reference only" ([BFL FLUX.1 Tools](https://bfl.ai/blog/24-11-21-tools)) — a strategic signal that BFL moved its control story to instruction editing with references, and the reason community unions are now the numeric-control path. And a caution that applies to any evaluation gate: a 2026 RL paper names a **collapse mode** where "baseline models spuriously inflate scores by simply copying the reference scene" ([arXiv 2607.29025](https://arxiv.org/pdf/2607.29025)). A model that "preserves identity" by refusing to change anything has achieved stasis, not determinism — which is the same trap the existing `align` stage already hit from the other direction when lowest palette distance selected the emptiest frame.

## The 3D proxy is a real high-control option, not standard professional practice

The premise that "model the hero asset once in 3D, render exact camera angles, then style with depth/normal ControlNet" is standard professional practice **is not supportable as written.** No independent, journalistic breakdown of a shipped brand commercial or music video crediting a grey-proxy → depth-ControlNet pipeline was found; searches for studio breakdowns returned tool writeups. What *is* true is that 3D-as-direction-layer is professionalizing: Autodesk Flow Studio shipped a 3D Editor plus a node-based Canvas where "the 3D scene does not necessarily produce the final pixels" but sets staging, composition and camera, and co-founder Nikola Todorovic's own adoption curve runs social → commercials and independents → **major studios still ahead, not here** ([fxguide, 2026-08-24](https://www.fxguide.com/fxpodcasts/nikola-todorovic-on-autodesk-flow-studios-new-3d-editor-canvas/)). Named practitioner projects exist — HEIST ran Character Creator → iClone previs → AI generation, with shots "reviewed and approved in 3D before any AI generation" ([Reallusion Magazine, 2026-06-26](https://magazine.reallusion.com/2026/06/26/ai-studio-storytellers-heist-previz-to-production-the-3d-to-ai-workflow/)) — but HEIST drove composition through AI Actors and prompts, not depth passes.

The balanced verdict comes from the one source that publishes an effort/control table across the whole spectrum. Flick rates **motion reference (video→video) as low–medium effort and high control, render passes plus ControlNet as high effort and very high control**, greybox plus character rig as medium effort and high control, and concludes: "For the bulk of narrative work, the motion reference model provides the sweet spot" ([flick.art](https://flick.art/blog/blender-ai-filmmaking)). That is the recommendation to adopt: **reserve pass-driven control for the shots where the skiff must match exactly, and use the cheaper levers elsewhere.**

The documented recipe is consistent across sources and short. Build **untextured proxy geometry where only the silhouette has to be right** — "a character is a capsule with a head" — with accurate scale, ground and horizon blocked, and **the camera placed early, because framing determines which geometry matters** ([Mixar](https://www.mixar.app/blog/blender-blockout-to-video)); NVIDIA's own blueprint agrees that "detailed models and high-quality textures aren't needed because the scene is converted to grayscale" ([NVIDIA, 2025-04-30](https://blogs.nvidia.com/blog/rtx-ai-garage-3d-guided-generative-ai-blueprint/)). Render **depth plus a clay/flat-shaded pass**, with Mixar calling clay "the most useful single pass" because form and lighting read without colour interference, and **derive Canny from the clay render in post rather than rendering a Freestyle line pass**; add **cryptomatte object masks** when you want to regenerate the hero prop in isolation while leaving the background generation untouched ([RunComfy 3D Movie Pipeline](https://www.runcomfy.com/comfyui-workflows/3d-movie-pipeline-in-comfyui-ai-3d-scene-to-video-workflow); [fesq](https://medium.com/@iamfesq/3d-to-ai-masked-subgenerations-b329b686c7e8)). **Render at the generator's resolution, divisible by 64** — 480p–720p for Wan/LTX, not 4K — keep duration, frame rate and aspect identical across depth/clay/mask clips, and convert EXR or 16-bit output once to an intermediate and reuse it so the depth signal stays temporally stable (same RunComfy source). For the kneeling child, do not hand-model: **toyxyz's OpenPose-style Blender rig outputs depth, normal, Canny, OpenPose and segmentation from one posed rig in a single render** ([flick.art](https://flick.art/blog/blender-ai-filmmaking)), which converts a modelling problem into a posing problem.

For the fictional craft, image-to-3D removes most of the modelling cost. **Rodin Gen-2.5 is specifically aimed at hard-surface props, weapons and vehicles** with quad topology, and **TRELLIS.2 is a 4B sparse-voxel model under an MIT licence** that "kept the sculpted facets and texture closest to the photo" in a hands-on test; its documented weak spots — articulated joints, hair cards, engraved text — are irrelevant to a depth proxy ([trellis2.app](https://trellis2.app/blog/best-ai-3d-model-generator)). On this machine TRELLIS.2 runs only through a community MPS port needing ≥24 GB unified memory ([deepwiki: trellis-mac](https://deepwiki.com/shivampkumar/trellis-mac)), with sources disagreeing about whether texture export survives — verify against the repo, and ignore texture quality entirely. **The academic literature independently confirms that coarse proxies suffice**: LooseControl derives its condition from extruded planes and approximate 3D bounding boxes, controlling "only the approximate position, orientation, and size of objects" ([arXiv 2312.03079](https://arxiv.org/pdf/2312.03079)), and 3DProxyImg "uses only a coarse 3D estimate as a structural carrier," reporting better identity preservation and geometric consistency than video-based methods "without needing accurate geometry" ([arXiv 2512.15126](https://arxiv.org/pdf/2512.15126)).

Three honest caveats. **The 3D half of this is free on Apple Silicon**: Blender on Metal put the M4 Max GPU at **5,205 points across 38 Open Data tests, just under the laptop RTX 4080 at 5,326** and ahead of the RTX 3080 Ti and desktop RTX 4070 ([9to5Mac, 2024-11-17](https://9to5mac.com/2024/11/17/m4-max-blender-benchmark/)) — treat it as roughly tied with a 4070/3080 Ti rather than a clean win, since the tallies are crowd-sourced and launch-era. **Geometry and framing continuity across shots is the real payoff** (one scene, many cameras) but **no source documents a worked multi-shot example**, and **lighting continuity is explicitly unsolved by the 3D layer** — Mixar's position is that "the generated clip supplies its own lighting," which is exactly where cross-shot drift comes from. The downstream fixes are a clay pass rendered from every camera after lighting the scene once, shared reference stills, and a single batch colour-correction pass. And the only published time figure anywhere is Mixar's **"a blockout should take about twenty minutes"**, which almost certainly excludes building the compositor pass tree and normalising depth across shots — budget that one-time setup separately.

## Silhouettes survive a scene change; decals, panel lines and lettering do not

The most rigorous evaluation located is Photoroom's: four base models, **850 products**, all at 2K with the same prompt, **10 trained annotators with at least three reviewing every generation**, a custom side-by-side UI with independent pan and zoom, a 30-second minimum review time, and a generation marked failed **if any single annotator flags an issue** — chosen over majority voting because reviewers "tend to miss issues rather than invent them" ([Photoroom](https://photoroom.com/blog/top-editing-image-models-maintain-product-details-only-28-of-the-time)).

| Model | Pass rate (no fidelity issues) |
|---|---|
| Nano Banana 2 + Photoroom Fidelity Layer | 38.2% |
| Nano Banana 2 | **29.0%** |
| Nano Banana Pro | 28.2% |
| GPT Image 2 Medium | 27.2% |
| **FLUX.2 Klein 9B** | **16.8%** (plus ~28% outright invalid generations, vs 4–8% for the others) |

But the failure-mode breakdown matters more than the leaderboard: **logo/text distortion 20.1%, missing or changed elements 12.5%, pattern or design changes 11.4%, colour shifts 8.1%, virtual try-on failures 6.7%, wrongly added elements 4.8%, material/texture changes 3.1%, and shape/cut/fit changes just 1.5%** (same source). **Shape is the rarest failure by an order of magnitude.** For a scratch-built hover-skiff that means the overall silhouette will probably survive a scene change, while decals, panel lines, lettering, insignia and small protruding parts are what will drift. Two design consequences follow directly: minimise fine surface detail the model must reproduce, and plan to composite markings back in rather than asking for them. Photoroom is a vendor whose own correction layer tops its own leaderboard, and the benchmark covers apparel and accessories rather than rigid props, so transfer to a skiff is unproven — but the methodology is the strongest in this field and the shape-versus-detail split is the kind of structural result that should transfer.

The awkward part is that **klein 9B is the worst performer in that benchmark and is also this project's still model**, chosen because it is the most Mac-friendly option. The Apple-Silicon-local path and the fidelity-leading path do not currently coincide. That is an argument for two things rather than for abandoning klein: move geometry out of klein's hands into ControlNet, and keep a human review gate, since even Photoroom's own correction layer only lifted 29.0% to 38.2%.

**A made-up object needs one reference per side that appears on screen, or the model invents the hidden geometry.** This is the most actionable single practitioner finding in the research: Runware's test used a front-only denim reference and got a plain back; **adding a back reference brought through an embroidered design the prompt never mentioned** ([Runware character-consistency guide](https://runware.ai/docs/models/google-nano-banana-2/guides/character-consistency)). Treat that as a rule, not a tip — "a single reference only carries what it shows." This project's existing turnarounds via `seed_sheet.sh` (front / three-quarter / side / back, plus arbitrary prompt-sentence views) are already the right apparatus; what changes is that **the turnaround stops being documentation and becomes the reference set fed per shot**, with the chosen views matching the angles the shot actually shows. Kling's element system is the closest commercial analogue — an element is **1 main plus up to 3 supplementary references**, with front/side/back/detail recommended ([Kling Element Library guide](https://kling.ai/quickstart/klingai-element-library-3-user-guide)) — which is a direct validation that the model-sheet approach is what the commercial systems converged on too.

On prompt form, BFL publishes the only explicit role taxonomy in any vendor documentation, and it names objects. For multi-reference editing you declare what each image supplies: **Subject** (a person, animal or character to keep recognisable), **Product** (an object whose *shape, colour, or label should stay the same*), **Setting** (scene or background), and **Style** (palette, medium, texture, lighting) — one image may supply several roles, and you must also state how the pieces relate spatially ([BFL multi-reference editing](https://docs.bfl.ai/guides/prompting_editing_multi_reference)). The published template sentence is the one to copy for the skiff: **"Put the ceramic mug from image 2 on the shelf in image 1, keeping the mug's glaze and the room unchanged"** — source, destination, and what must be preserved, in that order. Related mechanics: the first entry is "image 1", `aspect_ratio: auto` inherits image 1's ratio so the base scene goes first, inputs run 1–10 images each at least 256×256 and at most 16 MP, and **bounding-box rows are "a strong hint, not a hard constraint"** ([BFL editing overview](https://docs.bfl.ai/guides/prompting_editing_overview)) — so do not expect deterministic placement from the model; composite instead.

**Instruction form differs by model family, so per-model prompt templates are needed, not one shared string.** BFL documents imperative edit instructions ("Put the mug from image 2…"), while Qwen-Image-Edit-2511's own example is a scene description with explicit spatial roles: "The magician bear is on the left, the alchemist bear is on the right, facing each other in the central park square" ([Qwen-Image-Edit-2511 model card](https://huggingface.co/Qwen/Qwen-Image-Edit-2511)). No A/B study compares the two forms, so the divergence is inferred from the vendors' own examples — but reusing a Kontext-style imperative verbatim on Qwen is unlikely to be optimal. The five rules that *do* converge across all sources are: write the diff rather than the scene; name the subject with a concrete noun phrase instead of a pronoun; append an explicit preservation clause naming the attributes to hold; **do not re-describe what the reference already shows**; and make one change per pass ([ComfyUI Kontext docs](https://docs.comfy.org/tutorials/flux/flux-1-kontext-dev); [Runware](https://runware.ai/docs/models/google-nano-banana-2/guides/character-consistency)). There is a real tension between "name the attributes to lock" and "don't re-describe the subject," and the resolution is to name attributes as *constraints to hold* ("keep its panel lines and the yellow nose cone identical") rather than as *descriptions to render* ("a grey hover-craft with a yellow nose cone") — the latter invites synthesis from text, the former invites copying from the reference. One genuine documentation hole: **no source anywhere gives guidance for prompting a fictional object whose category the model has no prior for.** Every published recipe assumes a describable noun like "mug" or "sofa."

## Video: VACE names objects, but no Mac benchmark for it exists

VACE is the only system in this entire landscape whose documentation explicitly names objects. Its three modes — reference-to-video, video-to-video editing, and masked video-to-video editing — can be composed freely, with all inputs organised into a single Video Condition Unit ([VACE, arXiv 2503.07598](https://arxiv.org/abs/2503.07598)). The Wan2GP documentation describes reference images as a way to "inject people **or objects** of your choice in the Video" and to "force Images to appear at a specific frame nos," recommending you matte the subject onto white with a background remover and **name the injected subject in the text prompt** so the model connects it to the reference ([Wan2GP VACE.md](https://huggingface.co/spaces/attong39/Wan2GP/blob/main/docs/VACE.md)). That architecture is the only one where you can stack reference stills, a depth or pose control video, masks and keyframes simultaneously — and both Wan VACE and LTX support LoRA training, so it is also the only route where the object itself can be encoded into weights rather than inferred by a general encoder.

**But VACE should be treated as unavailable on this machine for planning purposes.** Kijai's Wan 2.2 VACE release is only the VACE blocks, built mainly for WanVideoWrapper, and the one native-loading report found was a user saying it did not work for them ([Kijai discussion #81](https://huggingface.co/Kijai/WanVideo_comfy/discussions/81)). **No timing data for VACE on any Apple hardware was found, from any source.** It sits on top of the exact Wan-under-ComfyUI path that measures at **1 h 22 min for 2 seconds of 832×480 video on an M1 Max** via Q4_K_S GGUF ([lilting.ch](https://lilting.ch/en/articles/ltx2-wan22-mac-local-video-gen)), and no source confirms that the GGUF loader nodes (ComfyUI-GGUF, KJNodes `GGUFLoaderKJ`) are fully functional on Metal. A third-party guide does give M4 Max 48 GB figures of **2–4 min per Wan 14B FP8 clip** ([willitrunai](https://willitrunai.com/blog/wan-2-2-vram-requirements)), but the same page's internally inconsistent FP16-on-Mac claim and the measured FP8-on-Metal failures make it unsafe to plan against. The defensible reading: VACE is the architecturally right answer and the practically wrong one here, and it becomes the right answer the day an NVIDIA box enters the picture.

Two version facts correct the generational framing. **Wan 3.0 is API-only** — launched as a closed beta on Alibaba Cloud Model Studio as `wan3.0-video`, with no weights on the Wan-AI HF org, the Wan-Video GitHub org, or ModelScope, and **Wan 2.2 remains the current official open-weight Wan generation** ([reapi](https://reapi.ai/blog/is-wan-3-0-open-source)); one page claiming an Apache-2.0 pre-announcement is contradicted by every other source and should be treated as rumour. And **LTX has native keyframes but no reference-identity conditioning.** The mechanism is architecturally explicit: first-frame conditioning *overwrites* the tokens at first-frame positions, while later keyframes are *appended as separate keyframe tokens* via `prepare_keyframe_extras`, each carrying a conditioning mask at the requested strength ([HF Diffusers LTX2 docs](https://huggingface.co/docs/diffusers/api/pipelines/ltx2)). Identity is not in the base model — there is an open feature request asking Lightricks for "True Reference Image Conditioning for LTX 2.5," arguing it "would remove the need to train and manage custom LoRAs for strict character, **asset, and environment** consistency across shots" ([Lightricks/LTX-2.5 discussion #46](https://huggingface.co/Lightricks/LTX-2.5/discussions/46)). Community substitutes exist (an MSR multi-reference LoRA, a prefix-injection reference-conditioning node) but are weeks-to-months-old unvalidated code. Lightricks' own recommended identity route remains **character LoRA training**, described as giving "the deepest identity encoding for varied angles and lighting" ([ltx.io](https://ltx.io/blog/how-to-maintain-character-consistency-in-ai-video)). One informal but pointed datum: baseline LTX generations with no LoRA "showed clear errors in motion, object consistency, and character detail" ([mindstudio](https://www.mindstudio.ai/blog/ltx-2-5-comfyui-install-guide)).

The reference-versus-keyframe mutual exclusivity trap is model-specific and schedule-relevant, because for a multi-shot film you want both "this is my ship" and "this shot starts here and ends there":

| Model | References + keyframes together? |
|---|---|
| **Seedance 2.5** | **No** — the API actively rejects reference fields on prompt-only, first-frame and first+last-frame requests ([atlascloud](https://www.atlascloud.ai/models/bytedance/seedance-2.5/reference-to-video)) |
| **MiniMax H3** | **No** — up to 9 references, but "cannot be combined with start or last frame fields" ([pixeldojo](https://pixeldojo.ai/ai-video-models-that-accept-reference-images)) |
| **Kling 2.6** | **No** — "Start Frame + Element Reference" is marked unsupported; it is a 3.0 feature ([Kling VIDEO 3.0 guide](https://kling.ai/quickstart/klingai-video-3-model-user-guide)) |
| **Kling 3.0 / O1 / O3** | Yes — `start_image`/`end_image` plus 4-image elements |
| **Veo 3.1** | Yes — `reference_images` (3 max, "person, character, or **product**") plus `image` + `lastFrame`; reference clips are forced to 8 s; preview endpoints reportedly retiring 2026-10-22 ([buildfastwithai](https://www.buildfastwithai.com/blogs/google-veo-3-1-ai-video-generator)) |
| **Luma Ray3** | Yes — character reference combines with keyframes, but it is **single-reference** and face-oriented ([Luma Ray3](https://lumalabs.ai/ray3)) |
| **Runway Gen-4.5** | First-frame only, and **no region or mask parameters at all** ([Mervin Praison survey](https://mer.vin/2026/09/which-ai-video-models-actually-take-a-first-and-last-frame/)) |
| **Wan 3.0** | First-frame only, despite being the newest generation |
| **VACE (open weights)** | Yes — the only route stacking references, masks, control video and keyframes at once |

The operational hazard across all of them: **passing two frames to a first-frame-only model does not error — it ignores both images and bills you for a prompt-only clip** (same survey). Any comparison test must verify per model that the last frame actually influenced the output, or a dropped input will be recorded as a consistency failure.

Three craft findings transfer regardless of model. **Chaining drifts predictably**: FramePack's own stress test says "the result will mess up quickly after you do this 5 or 6 times, and everything will severely degrade after you do this about 10 times" ([FramePack](https://lllyasviel.github.io/frame_pack_gitpage/)), and the mechanism is codec loss plus anchor fade — each extension reads a *compressed* copy of the previous clip's final frames and treats them as ground truth ([screenweaver.ai](https://www.screenweaver.ai/blog/ai-video-extension-quality-loss)). The rules that follow are concrete: extract handoff frames as PNG from the highest-quality render, never from a delivery encode or a preview; re-anchor to the original reference every 2–4 handoffs; and hide the reset behind a cut. **Keyframe gaps should be short**, because generative inbetweening's known weakness is temporal instability that grows with the motion gap between the two keyframes ([FCVG, arXiv 2412.11755](https://arxiv.org/pdf/2412.11755)) — many short pinned segments beat two distant keyframes with a big action between them. And **a locked camera genuinely helps, but nobody has proved it**: the mechanism is agreed (large orbits force the model to invent geometry the reference never showed) and the recurring prompt pattern is "one still-camera sentence, one subject or environment motion clause, zero extra camera verbs," with the caveat that a bare "static" tag often fails and explicit natural-language stillness works better ([prompting.systems](https://prompting.systems/blog/prompts-for-maintaining-temporal-consistency-in-ai-video); [magichour](https://magichour.ai/blog/how-to-keep-characters-consistent-in-ai-video)). **No controlled study isolates camera stillness as the cause of better identity retention, and no evidence at all exists for camera moves degrading *object* geometry specifically** — but the argument is stronger for a prop than for a face, because invented sides are exactly where a LoRA constrains least. This project's s7 failure (a locked side-view still whose video prompt asked the camera to hold below the falling craft, after which the hull became a wheeled machine with two lenses) is a textbook instance, and the s8 success beside it is the control.

## The evidence gap: nobody has run the test this film needs

**There is no published side-by-side test of a made-up mechanical object held across multiple shots, in any source examined.** This is not an omission. Every identity benchmark located is face-only: the Face Consistency Benchmark is "specifically designed to measure the ability of video generation models to maintain consistent facial features" ([arXiv 2505.11425](https://arxiv.org/pdf/2505.11425)); Movie Gen's identity evaluation has human raters judge how well a generated face captures a reference person's likeness ([arXiv 2410.13720](https://arxiv.org/pdf/2410.13720)); Kaleido, the open multi-subject reference framework, reports face similarity on a curated human subset using two face-recognition metrics ([arXiv 2510.18573](https://arxiv.org/pdf/2510.18573)). Every practitioner product test uses a real consumer good — mug, serum bottle, headphones, vase — with one or a few generations per model, and the authors of the most careful one warn their screens "support within-screen judgments only; they are not a four-model league table" ([masonry](https://masonry.so/blog/best-ai-video-model-for-product-ads)). The only vehicle-identity paper found sits in the driving-simulation literature with a different method entirely ([Mirage, arXiv 2512.24227](https://arxiv.org/pdf/2512.24227)).

Worse, the pattern across those product tests is **a stability/motion tradeoff rather than a consistency ranking**: the models that kept the object intact also moved the camera least (Kling 2.6 "stayed close to the source but was nearly static"), and the models that moved the camera most invented detail (Kling O3 "added more visible parallax but invented side copy"). The published tests mostly establish which models *avoid* the hard case rather than which solve it. Two mechanisms make an invented craft harder than a real product in ways no existing test probes: the model has no prior for its shape and will regress toward familiar vehicle priors, and the invented features that carry the design — panel lines, greebles, insignia, asymmetric silhouette — are precisely the fine-detail and text-like elements that Photoroom's breakdown names as least stable.

**A reusable metric does exist, and it adapts directly to a vehicle.** The VideoMemory paper runs **Grounded SAM on each middle frame to localise the prop region, extracts DINOv2 features from the detected region, and compares them with features from the reference shot**, capturing whether the object "maintains a coherent visual appearance (e.g., color, shape, texture), even under changes in camera viewpoint or surrounding context" ([arXiv 2601.03655](https://arxiv.org/pdf/2601.03655)). Swap the detector for a vehicle prompt and that is a skiff-consistency score. This project already has most of the surrounding apparatus — `seed_sheet.sh` produces turnaround views, `qc_sheet.sh` produces reference-plus-N-frames contact sheets, `film_run.py` holds prompts and seeds fixed across shots, and the `eval` stage already scores views pairwise against each other with a documented calibration (a consistent turnaround at 0.006–0.010, a different object on the same backdrop at 0.216, an unrelated image at 0.753). **Replacing that palette histogram with masked-crop DINOv2 similarity is a small change that would produce the benchmark that does not publicly exist**, and the existing design decision to compare views pairwise rather than against the hero — holding the backdrop constant so what remains is the subject — is already the methodologically correct move.

## A LoRA locks the look; only structure locks the geometry

Say this plainly, because it reshapes the whole plan: **a LoRA does not reliably enforce geometry, part counts, or structural rules.** The clearest statement of the mechanism is that a FLUX.1-dev LoRA can learn style and texture but not strict rules, because the training loss only measures reconstruction of training images, not whether rules hold on new prompts — the model "is just not capable of strict rule enforcement by design" ([HF forum writeup](https://huggingface.co/datasets/John6666/forum3/blob/main/flux_lora_ft_rule_based_1.md)). Part-count failure is a **base-model** weakness the LoRA inherits rather than causes: state-of-the-art diffusion models systematically fail simple numeric constraints like "draw 5 objects," with accuracy dropping as numbers rise, and separate work reports that Stable Diffusion "often fail[s] to align with prompt-specified object quantities" ([CountSteer, arXiv 2511.11253](https://arxiv.org/pdf/2511.11253)). The recommended architecture from the same source is explicit: **generate the constrained geometry outside the model, render it, feed it to a Canny or Depth conditioning path, and limit the LoRA to style** — material, texture, short captions, one trigger token — with a programmatic checker filtering outputs. Expect a prop LoRA to carry palette, material, surface finish and gestalt proportions reliably, and to carry discrete part counts and exact topology unreliably. **Budget the look lock and the geometry lock as two separate mechanisms.**

The hyperparameter consensus band, assembled from several sources with no object-specific sweep published anywhere: **rank 16–32 with alpha at or below rank** (rank 32 is the recommended FLUX.2 default, with an explicit warning that ranks of 4–8 have little effect on the fused blocks — [RunComfy](https://www.runcomfy.com/trainer/ai-toolkit/flux-2-dev-lora-training)); **LR 1e-4**, dropping to 5e-5 and resuming from the last good checkpoint if samples overshoot, and doubling to 2e-4 if batch size goes to 2 ([Civitai 7777](https://civitai.com/articles/7777/detailed-flux-training-guide-dataset-preparation)); **batch 2 plus gradient accumulation 2** unless batch 4 fits, with ≥2 images per aspect-ratio bucket; **1,000–3,000 steps** for a subject; and **10–50 images**, since FLUX "seems to train best with a low number of images, anywhere from 10 to 50" (same Civitai source). Train at 512 for most LoRAs and 1024 only for very fine detail — noting that on Apple Silicon the MPS resolution ceiling lands a 64 GB machine around 768 px, so the fine-detail-at-1024 option is effectively unavailable, which is itself an argument for structural conditioning over brute-forcing detail into weights.

Object captioning differs from person captioning in two specific ways. **Use `<rare-token> <class noun>`** — "skslume lamp" — with the trigger in front of the object's real noun, spelled, spaced and capitalised identically in every caption and every validation prompt, so the base model still has a prior to attach to. **Cover every side that defines the object** — seams, openings, controls, permitted labels, and how the material responds to light — rather than aiming for mechanical angular coverage. And **vary framing hard**: "Don't let every object fill the same share of the frame, or FLUX may learn the composition along with the product," and avoid aggressive centre crops that remove defining features ([LocalForge AI](https://offlinecreator.com/guide/flux-lora-training-dataset-guide)). The documented failure modes are all dataset-design symptoms — sticky recurring backgrounds, outputs copying training compositions, a trigger with little effect from spelling drift, and good training samples alongside weak real prompts because validation prompts sat too close to the captions. One cheap, high-value design decision for an invented asymmetric craft: **add a deliberate asymmetric marking**, which fixes front/back ambiguity in the dataset and gives a human reviewer an instant continuity check across shots. For stacking a character LoRA with a prop LoRA, start the character primary around 0.7–1.1 and the object secondary around 0.2–0.6, test each alone first, compare at a fixed seed, and composite in separate passes rather than fighting the weights if the prop degrades the face ([eastondev](https://eastondev.com/blog/en/posts/ai/20260720-comfyui-lora-guide/); [neurocanvas](https://neurocanvas.net/blog/multi-lora-workflows-comfyui/)). Train both at the **same rank** from the start, because merging in Diffusers requires equal ranks ([diffusers merge_loras](https://huggingface.co/docs/diffusers/v0.31.0/using-diffusers/merge_loras)).

**The Draw Things LoRA format trap is the single most likely way to lose a day on this machine, because it fails silently.** A `.safetensors` LoRA placed in the models folder and passed to `draw-things-cli` **runs without error and has no effect.** Draw Things only loads LoRAs in its own format, `<name>_lora_f16.ckpt`, **registered in `custom_lora.json`** — and while the *app* converts files on UI import, **the CLI does not** ([vcspr/drawthings-lora-convert](https://github.com/vcspr/drawthings-lora-convert)). That project builds Draw Things' own official `LoRAConverter` from source with SwiftPM, converts, registers with a backup, and — critically — ships a `verify` command that renders the same seed with and without the LoRA to confirm it applied; first build takes roughly 25 minutes. Any automated pipeline importing third-party LoRAs must call the converter and then verify, because the failure is quiet rather than loud. The reverse direction is worse: the community Draw Things → safetensors converter extracts tensors from the SQLite container but is marked **archived research with an explicit "do not rely on it," and it skips compressed or quantised tensors** — which covers most real Draw Things files ([bkohlberger converter](https://github.com/bkohlberger/Draw-Things-to-Safetensors-Converter)). **Conversion out of Draw Things is effectively broken for anything quantised.** The only reliable export route is the app's own native LoRA export for LoRAs you trained in Draw Things — which is also the reason training there keeps a cloud escape hatch open, since an adapter trained in Draw Things can leave the machine while a quantised `.ckpt` cannot.

## The recommended pipeline: ten stages, and what replaces the dice roll at each

The measured numbers on this exact machine are the planning basis, and they are better than any published ComfyUI-on-Mac figure by one to two orders of magnitude:

| Job | Settings | Measured here |
|---|---|---|
| FLUX.2 klein 9B still (`i8x`) | 1280×768, 4 steps, DDIM Trailing, shift 3.0 | **27–35 s per seed** |
| klein single-image edit | 576×1024, strength 1.0 | **≈30 s** |
| klein diptych (ref + input) | 1152×1024 | **45–60 s**; 1–2 of 3 seeds keep identity |
| LTX-2.3 22B distilled 1.1 (`q8p`) clip | 1024×576, 249 f @ 25 fps (10 s), 8 steps | **580 s = 9 min 41 s** (53 s/step), ~2× faster than the app |
| Wan 2.2 I2V | 576×1280, 81 frames | **24 min** |

All from `wiki/headless-cli-pipeline.md` §1b/§1c and `wiki/draw-things-setup.md`. For contrast, ComfyUI plus Wan 2.2 Q4_K_S GGUF on an M1 Max took **1 h 22 min 45 s for 2 seconds** at 832×480 ([lilting.ch](https://lilting.ch/en/articles/ltx2-wan22-mac-local-video-gen)). The planning rates that follow: roughly **1 minute of wall clock per second of finished LTX video**, ~18 s per Wan 2.2 frame at 576×1280, and 2.5–3 minutes per approved image-conditioned still at three seeds. A 12-shot film at 5 s per shot is about an hour of LTX render plus 30–40 minutes of still selection plus upscaling — an overnight batch.

**48 GB is not the binding constraint; time is.** The largest confirmed single load is ~24 GB (Wan 2.2 14B Q4 GGUF pair plus umT5 plus VAE), and Draw Things' Wan 2.2 14B 6-bit load at 1024×576×81f is ~20 GB. Memory binds in exactly two places: concurrency — **running the generator and the upscaler simultaneously is not advisable** — and the PyTorch FLUX-training path, already ruled out on other grounds. Also remember the reporting trap: Activity Monitor shows ~0.5 GB RSS while 26 GB of LTX plus 13 GB of Gemma are mmap'd, and the CLI's TTY spinner means a redirected log stays empty until the process exits, so judge progress from `lsof` or RSS.

| # | Stage | What replaces "roll 3 seeds, rank by palette distance" |
|---|---|---|
| 1 | **Design lock.** Hero still of the skiff and the droid, hand-fixed until exactly right; add a deliberate asymmetric marking; minimise fine surface detail the generator must reproduce. | Nothing — this is already the right step. The new constraint is a design rule, not a sampling rule. |
| 2 | **Model-sheet masters.** `seed_sheet.sh` turnarounds (front / three-quarter / side / back, plus any view a shot needs) for every recurring asset, with `master_views.kind` set to `person` or `object`. | Unchanged, but the views are now **production inputs**, selected per shot to match the angles on screen — the Runware denim rule. |
| 3 | **Coarse 3D proxy.** Image-to-3D the skiff from the hero still (TRELLIS.2 locally, Rodin Gen-2.5 hosted), patch it with boolean primitives where the mesh fails, ignore texture entirely. Rough-block the droid and the two desert environments as primitives. | The craft's geometry stops being re-synthesised from text or inferred from a reference. ~20 min per blockout once the pass tree exists. |
| 4 | **One scene, many cameras.** Place every shot's camera in the single proxy scene; light the scene once. | Cross-shot framing continuity becomes a property of the scene file rather than an outcome of prompt similarity. |
| 5 | **Pass render.** Per shot: depth (Z pass, normalised with a **fixed** near/far across the whole shot) plus a clay/flat-shaded pass; derive Canny from the clay in post; cryptomatte masks for the skiff and droid. Render at the generator's resolution, divisible by 64. For the kneeling child, pose toyxyz's rig and take depth/Canny/OpenPose/segmentation from the single render. | This is the replacement for seed-rolling on composition. Layout, scale, occlusion and camera distance arrive as an image. |
| 6 | **Conditioned still render.** `draw-things-cli --config-json` with `controls[]` carrying depth at scale ~0.8 and `start_percent 0`, Canny second at a reduced scale so the total lands ~0.7–0.9, plus `loras[]` for the child. Fixed seed. Keep the combo-master and edit-off-combo structure. | **The core replacement.** One planned render per shot instead of three candidates and a ranking. Seeds become a tie-breaker for texture, not a search over layouts. |
| 7 | **Masked fix-up.** Inpaint markings, insignia and panel detail back in against the cryptomatte mask, same sampler and scheduler as pass 1, low denoise. | Addresses the 20.1% logo/text and 12.5% missing-element failure modes directly, instead of hoping a seed gets them right. |
| 8 | **Review gate.** Human look at the picked stills before the clip stage spends an hour. Score with masked-crop DINOv2 similarity against the master (VideoMemory method) in place of the palette histogram, keeping the existing pairwise-views design and the sharpness floor. | Replaces a metric that provably picks the emptiest frame with one that localises the subject and compares its appearance. Keeps the human in the loop, because no metric distinguishes "the right craft" from "a crisp wrong one." |
| 9 | **I2V with the camera locked and gaps short.** LTX-2.3 via `--image` + `--frames` (frame 0 is the still, pixel for pixel). Video prompts say what moves inside the frame, never where the camera goes; where a move is unavoidable, keep it on the side the still already shows. Pin both ends with hand-authored stills where the model supports it; re-anchor to the original reference every 2–4 handoffs and put a cut at the reset. | Replaces "generate and hope the hull survives 249 frames." The still plus a locked camera is the geometry constraint; keyframes are the second one. |
| 10 | **Finish.** Real-ESRGAN to 4K, one base LUT per lighting setup applied at 50–80%, shot-by-shot match to a single reference still, then a **uniform grain pass last over everything** (gaussian blur 0.3–0.6 px, 35 mm or 16 mm grain at 8–15%), which is what makes clips from different generations read as one piece ([invideo](https://invideo.io/blog/ai-color-grading/)). | Colour and texture continuity move from per-shot luck to a post discipline. |

**Keep, because it already matches professional practice:** the model-sheet master turnarounds (Kling's element system independently converged on 1 main plus 3 supplementary references with named angles); the combo/composed-group masters on a plain backdrop, which is the correct answer to "preserve a group *and* invent a landscape is two jobs and the hull loses"; the instruction-form edit prompts at `--strength 1.0`, which match BFL's documented imperative template; the **edit-off-combo rule** — once a group is a picture, it is edited, not re-composed — which is the single best piece of local craft in the repo and has no published equivalent; and the locked-camera video prompts stated positively, which match the one prompt pattern that recurs across every practitioner source. **Replace:** candidate generation as the mechanism for getting composition right; palette distance as the identity metric; text-only invention of the skiff's geometry in any shot where it must match; and any plan that waits for an identity adapter on Apple Silicon.

**Effort estimate.** The one-time setup is the real cost: a Blender compositor pass tree with stable depth normalisation and a shot naming convention, plus a `controls[]` config template per render type, plus the DINOv2 swap in `eval` — call it two to four focused sessions, with the image-to-3D port install and the LoRA converter build each eating an hour or more of their own (the converter's first build is ~25 minutes; the MPS TRELLIS port needs a verified Hugging Face account and carries a non-commercial RMBG-2.0 dependency). Per-shot marginal cost after that is roughly 20 minutes of blockout and camera work plus 1–2 minutes of conditioned render — which is *cheaper* than three diptych seeds at 45–60 s each followed by a rejection and a redo, as soon as the redo rate is non-trivial.

**Staged adoption, biggest gain first.** (1) **Prove `controls[]` works headlessly** with a depth map of the existing skiff master on a single shot, at depth 0.8 / start 0 / end 0.8 — this is one evening and it either unlocks everything downstream or it does not. (2) **Swap `eval`'s palette metric for masked DINOv2**, because every later decision depends on being able to measure drift, and this is the cheapest change in the list. (3) **Blockout and pass-render the two or three shots that already failed** — s3, s6, s7 are documented failures with known-good comparisons, so they are a ready-made A/B. (4) **Train the skiff LoRA at the same rank as the child's**, rank 32 / alpha 16, 25–40 images from the turnaround plus proxy renders, captioned `trigger + class noun + view/lighting/background` and nothing about the craft's intrinsic design — accepting that it locks the look while ControlNet locks the geometry. (5) Only then consider the droid's own adapter or any cloud GPU work. One number is missing and should be obtained before step 4 is scheduled: **no measured wall-clock time for any LoRA training run on an M4 Max exists in any source**, from Draw Things, mflux, or anyone else. Whether that step is an afternoon or a week is genuinely unknown.

## Conclusion

The deepest shift this research forces is a change in what the pipeline is *for*. The current design treats generation as a search — produce candidates, score them, pick — and every improvement within that frame is an improvement to the scorer. But the professional pattern is not a better scorer; it is **moving the decision out of the sampler entirely**. Composition is decided by a camera in a 3D scene, geometry by a depth map, identity by trained weights, and the sampler is left with the one job it is actually good at: rendering surface. The ControlNet correction matters not because it adds a feature but because it was the missing piece that made that frame impossible on this machine — and it turns out it was never missing, just addressed through JSON rather than a flag. The corollary is uncomfortable and worth stating: the existing `align` stage's discovery that lowest palette distance selects the emptiest frame was not a bug in the metric. It was the search frame telling the truth about itself, because **no appearance metric over whole frames can distinguish a correct render from a confident wrong one**, and the fix is to stop asking it to.

The second shift is about where to expect trouble. The instinct with an invented mechanical asset is to worry about the silhouette; the data says the silhouette is the *safest* thing in the frame at a 1.5% failure rate, and the danger is concentrated in markings, lettering and small parts at 20.1% and 12.5%. That reverses the design priority: spend the effort on a proxy that fixes proportion and camera, keep the skiff's surface deliberately plain, and composite the insignia. The third, and the one with the longest tail, is that **this project is closer to the research frontier than the frontier is to this project.** There is no published test of a made-up mechanical object held across shots, the only prop-consistency metric in the literature is a two-component recipe this repo could implement in an afternoon, and the apparatus — turnarounds, contact sheets, fixed seeds, a pairwise-views evaluator with a published calibration — is already built. The benchmark that does not exist is cheaper to generate here than to wait for, and a film with a child, a scratch-built skiff, a droid and two deserts is a better test subject than another serum bottle.
